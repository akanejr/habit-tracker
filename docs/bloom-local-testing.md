# Local session milestone and test notes

**Not a hosted migration or a release.** `/bloom-local` is a development-only route, disabled unless `BLOOM_LOCAL_SESSIONS_ENABLED=1`, the public Supabase URL uses a literal loopback host, and a signed-in local user exists. The normal `/dashboard` is still the old dashboard. The local UI is wired to the RPCs and tables in `supabase/local-only/session_foundation.sql`; it has not been end-to-end tested against a real local Supabase Auth/PostgREST stack. The browser's loopback address is the browser machine, not the hosted workspace; remote preview requires a separately designed local proxy.

## Changes in this milestone

- Local-only SQL adds sessions, timed segments, owner read policies, partial unique indexes, legacy-log backfill with reconciliation, habit history preservation, a default-on persistent freeze, and owner-scoped idempotent RPCs for create/edit/archive, start/pause/resume/complete/cancel and Quick Log. Old direct habit and log writes stay fenced even when new RPCs are released. The restricted freeze allowlist exists only for local test users. The SQL does not include goal scheduling or account deletion; do not apply it to hosted databases, and do not place it in the automatic migrations directory.
- The local UI includes Today, persisted server timer recovery, a non-stopping four-hour warning, Quick Log while a timer is active, an uncertain-response retry using the same request UUID, habit editing/archive, session and known version history, weekly session/day/time summaries, theme preference, loading/offline/error states and confirmation prompts. Goals and account deletion are explicitly unavailable. Server RPC time is authoritative; the clock in the UI is only an estimate.
- The retry payload lives in per-tab session storage, including any Quick Log note, until success or an explicitly confirmed discard. It survives a refresh in that tab but is not a durable cross-device queue; clearing browser data or closing the tab can lose the retry. Refresh and check history before repeating an action with a new ID. Session history is paginated, but multiple pages are not a transactional snapshot under concurrent writes.
- The full user-facing app is **not complete**. In particular the main dashboard is unchanged; current local SQL and the local route must not be used for release. Goals, accurate goal-aware reports, account deletion, real Auth/PostgREST integration and recovery remain open. Four-hour warning, accessibility and mobile layout have only the limited mocked-browser coverage below.

## Evidence from the disposable PostgreSQL instance

PostgreSQL 17.11 was extracted locally into `/home/user/bloom-pg-runtime`; it listened on a user-private UNIX socket only, with no TCP listener. The database tests create and drop only freshly named `bloom_test_<random>` databases on that specific socket. They replay the four recorded baseline migrations and the local-only SQL using synthetic rows. A minimal `auth.users` table and `auth.uid()` stub simulate database identities: this is **not Supabase Auth, real JWT validation, PostgREST, Storage or a hosted catalog**.

`python3 tests/session-db.integration.py` passed 54 checks on the current SQL: legacy backfill, RLS owner isolation, direct-write and deletion denial, freeze/release, idempotency including concurrent retries, 14 same-day sessions, timer transitions and archived completion, eight start/archive races, and synthetic Auth-row deletion, rollback on a blocking foreign key, stale identity and one deletion/write race. These checks do not prove all race interleavings or a complete account-deletion workflow. The database is dropped by the test; it does not touch a hosted connection.

`python3 tests/wal-observation.integration.py` ran against the same isolated instance after setting `wal_level=logical` and restarting it. With `track_commit_timestamp=off`, PostgreSQL's `test_decoding` emitted the transaction's commit timestamp after the row write timestamp. The temporary replication slot and database were removed. This is evidence for an investigation, **not a durable consumer or a working scheduling solution**.

To recreate the test server on Debian 13 without installing services globally, extract the Debian `postgresql-17` and `postgresql-client-17` packages under `/home/user/bloom-pg-runtime/root`; initialize a fresh data directory as a non-root user with the extracted `initdb -L .../usr/share/postgresql/17`; set `listen_addresses = ''`, `unix_socket_directories = '/home/user/bloom-pg-runtime/socket'`, `unix_socket_permissions = 0700`, `port = 55439`, and `dynamic_library_path` to the extracted PostgreSQL library directory. For the WAL observation set `wal_level=logical` before startup. Start `postgres` as a supervised foreground process, not against an existing or hosted server. The scripts verify an empty `listen_addresses` and `inet_server_addr() IS NULL` before creating synthetic databases. Stop the server and remove the disposable runtime after testing.

## Browser test

`tests/session-ui.mock.mjs` uses Playwright, a test-only page copied from `tests/fixtures/bloom-harness-page.tsx.fixture`, and in-memory intercepted PostgREST responses. **The fixture must never be copied into the shipped application tree.** It does not test Supabase Auth, PostgreSQL or real API/network permissions.

In a disposable copy without any `.env*` files, copy the fixture to `app/bloom-harness/page.tsx`, install dependencies and Playwright Chromium, and start Next with the synthetic environment `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321` and `NEXT_PUBLIC_SUPABASE_ANON_KEY=synthetic-test-only` on port 3100. The mock intercepts requests, so there is no backend at that address. Run `node tests/session-ui.mock.mjs` with Node 22. The app must be reached at `http://localhost:3100/bloom-harness` for this harness. Browser libraries may need installation in the test environment. Remove the temporary copy afterward.

The test passed in one 390px dark-mode Chromium viewport: initial axe scan with zero detected violations, offline disabling, timer start/reload/pause/resume, four-hour warning, Quick Log during timer, an intentionally lost response and same-request retry after refresh, history, archive then completion, Progress, disabled deletion, and no horizontal overflow. An automated axe scan is not comprehensive accessibility validation. The mock cannot prove SQL/client integration.

## Goal scheduling investigation

The previous candidate uses `pg_xact_commit_timestamp`, which PostgreSQL can discard after vacuum. The logical-replication protocol's COMMIT message contains the actual transaction commit timestamp (PostgreSQL 17 documentation: https://www.postgresql.org/docs/17/protocol-logicalrep-message-formats.html). A future design could potentially consume a pre-established replication slot, durably store goal-change ID, transaction identity, commit timestamp, commit/end LSN and effective Lagos week, and acknowledge only after durable storage; replay must be idempotent. It must fence new goal writes whenever continuity, retention or the consumer's health is uncertain. Slot loss, WAL/disk exhaustion, long consumer outages, failover, restart, backup/restore, multiple changes in one transaction, ordered history, permissions and zero-gap bootstrap need an implemented and tested solution. SQL `pg_logical_slot_get_changes` can advance a slot before application-side durable capture, so it is not a safe substitute for a crash-safe acknowledgment protocol. `test_decoding` was only an observation and is not proposed as the production consumer. Hosted replication settings, privileges and viability remain unknown; no hosted inspection has been performed.

## Account deletion and cutover limits

The synthetic cascading tests demonstrate only PostgreSQL behavior for this relationship graph. A real deletion flow needs identity verification and recent reauthentication, a user confirmation, an account-wide fence shared by all write/read paths, authenticated secure execution with no service-role key in the app, handling of Storage and other external resources, retries and partially completed deletion, surviving JWT/session checks, and full Auth/Storage concurrency and failure tests. Neither a console instruction nor direct deletion of a synthetic Auth row is a user-facing feature. Supabase notes that an issued access token may remain valid until expiry and that owned Storage objects can prevent user deletion: https://supabase.com/docs/guides/auth/managing-user-data .

Before any release, separately authorize hosted catalog/ACL/writer inspection and prove the complete persistent freeze across old dashboard/habit edits and all privileged writers; back up and reconcile legacy data; validate local and authorized Preview testing; and test both pre-write rollback and lossless forward recovery after session writes. The local SQL's fence does not cover privileged/background writers or every profile/Auth/Storage path. Do not infer production safety from these tests.
